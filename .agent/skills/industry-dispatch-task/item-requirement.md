# 企业任务明细

任务有两层说明。企业端「任务跟踪」由任务系统把收到的 `items[].requirement` 原样展示。问题处置在冻结 JSON 里写结构化 `problems`，确认后按 SKILL.md 模板拼成 Markdown 表再提交；不要写 HTML。

| 层 | MCP 字段 | 写什么 |
|----|----------|--------|
| 共性 | `requirement` | 各家通用的目的、要求、时限 |
| 该企业 | `items[].requirement` | 仅当这家与共性不同、或有本企业对象（车牌/人员/记录）时必填 |

先判断任务类型，再套对应结构。**不要**把会议通知写成三类问题表。

问题整改、会议通知等统一冻结在 `pending_write/create.json`。每个可下发企业对应一个 `items[]`。问题处置冻结 `problems` 对象数组，不含企业全称；确认后拼成 Markdown 表写入 `requirement` 再提交。会议/培训/材料报送直接写短 Markdown 到 `requirement`。

## 如何选型

| 用户意图（含近义） | 落库类型 | 结构 |
|--------------------|----------|------|
| 整改、隐患、超载、违法、违规、限期纠正 | **问题处置** | `## 企业问题` / `## 车辆问题` / `## 驾驶员问题`，空类不输出 |
| 开会、调度会、宣贯会、座谈会、培训、考试 | **通知** | 会议/培训事项 / 时间地点 / 参加对象 / 需带材料 / 回执要求 |
| 报送、填报、上报材料、统计表、采集信息、摸底、核查名单 | **材料报送** | 报送目的 / 报送清单 / 口径与格式 / 提交方式 |
| 部署、转发文件、贯彻执行 | **工作部署** | 背景依据 / 工作要求 / 时间节点 / 责任与反馈 |
| 对不上上面几类的一般告知 | **通知** | 事项说明 / 具体要求 / 办理与提交 |

确认卡与 `dispatch_task_create` 必须带同一中文 `taskType`（通知 / 工作部署 / 问题处置 / 材料报送）。正文结构仍按上表选用，不要把会议通知写成三类问题表。

任务级 `requirement` 用 SKILL.md 固定句，不进确认卡。只要这家有企业指标、车辆、人员或记录，**必须**写该企业 `problems`（至少 1 条对象），不能用三句摘要代替。禁止编造源数据里没有的指标、车牌、人名、证件号。确认卡恰好 6 个字段，见 SKILL.md。

## 问题整改

企业明细只下发问题清单。不要「一、明细 / 二、问题分析 / 三、整改建议」。共性要求写在任务级 `requirement`。

节名只用：

- `## 企业问题`
- `## 车辆问题`
- `## 驾驶员问题`

没有记录的节整段不输出。只有车辆时仍写 `## 车辆问题`，不要改成「问题」或「1、」。

**企业问题 = 源材料没有精确到具体车辆、也没有精确到具体驾驶员的事项**，不是各车各人次数的合计。能精确到车牌 → 车辆；不能精确到车但能精确到驾驶员 → 驾驶员；两者都精确不到 → 企业。既有企业合计又有分车/分人明细时，只保留分车/分人行。

冻结时用 JSON 对象，不要手写 Markdown 表。车辆：**一对象一车**，必须有真实车牌。驾驶员：**一对象一人**，必须有姓名。没有车牌就不要写 `VEHICLE`。禁止「见车辆明细」「见上表」。同一车牌（或同一人）多种问题必须分成多条。禁止把多车或多人员写进同一对象或压成「超速N次」。`fact` 须含源材料已有的次数、已处理、里程、完整率。源材料提到或要求整改的问题全部入数组并下发，禁止因完整率达标、已处理、次数少、轻微或自行判断「太小」删条。仅当该条明确标注无需处理 / 不纳入整改 / 仅供参考不下发时才可省略。

字段：

- `kind`：`ENTERPRISE` / `VEHICLE` / `DRIVER`
- 企业：`occurredAt`、`problemCategory`、`problemType`、`fact`
- 车辆：`occurredAt`、`vehiclePlate`、`problemType`、`fact`
- 驾驶员：`occurredAt`、`driverName`、`problemType`、`fact`

不要「数据来源」。身份证号、资格证号默认脱敏。

仅有车辆时冻结：

```json
"problems": [
  {"kind": "VEHICLE", "occurredAt": "2026-09-12", "vehiclePlate": "晋L68222", "problemType": "超速", "fact": "超速7次，已处理7次"},
  {"kind": "VEHICLE", "occurredAt": "2026-09-12", "vehiclePlate": "晋LS0715", "problemType": "轨迹异常", "fact": "总里程530.25km，完整率97.69%"}
]
```

三类都有时放在同一个 `problems` 数组里。提交时按 SKILL.md 模板分组拼成三段 `##` 表，不要拼成一张宽表，也不要把数组再编码成 JSON 字符串。

**反例（禁止）：**

```text
【问题事实】晋L54990 9月12日超速7次，已全部处理。
【分析】单车单日超速频次极高。
【建议】核查当日行车轨迹。
```

写入 `pending_write/create.json` 的 `items[].problems`，条数对不上则补读源表后覆盖同一 JSON。出卡前必须检查：对象数组；一车一条或一驾驶员一条。手写 Markdown 表、多个对象挤一条、或「超速N次」无车牌/姓名 = 不通过。确认后禁止再读源附件、禁止改写 facts，只按模板拼表。单家接近 20 万字符时按时间段拆任务，禁止截断。

## 会议通知

```markdown
## 会议事项

召开全市道路运输企业第三季度安全生产调度会，通报近期突出风险并部署下阶段工作。

## 时间地点

时间：2026-10-15 09:00（请提前 15 分钟签到）
地点：市交通运输局 3 号楼 2 楼会议室

## 参加对象

你单位主要负责人、分管安全负责人各 1 人；不得无故缺席或由无关人员代替。

## 需带材料

- 本企业第三季度隐患排查治理台账
- 主要负责人安全生产职责清单

## 回执要求

请于 2026-10-12 前在企业端「任务跟踪」回复参会人员姓名、职务、联系电话。
```

未知的时间地点写成「以正式通知为准」或留待用户在确认卡补全，不要编造会议室。

## 培训通知

节名：培训事项、时间与方式、参加对象、需准备、考核与回执。线上培训写入口/平台名（仅用户提供的）。

## 材料报送

节名：报送目的、报送清单（多项用 Markdown 表：材料名称 / 格式 / 说明）、口径与格式、提交方式。

## 工作部署

节名：背景依据（文件名仅用户提到的）、工作要求、时间节点、责任与反馈。

## 信息采集 / 一般通知

采集：采集范围、指标口径、填报说明、提交方式。
一般通知：事项说明、具体要求、办理与提交。

## 确认卡

确认卡不展示各企业明细或摘要。缺 `pending_write/create.json`、缺卡上任一家 item、或任一 `problems` 检查不通过：禁止出卡。确认后只 Read 这一份 JSON，拼表后提交。读不到则停止并重新出卡。
